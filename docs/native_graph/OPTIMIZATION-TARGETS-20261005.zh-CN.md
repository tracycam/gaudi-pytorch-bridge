# 收益审计：先优化实际完成时间

本轮没有改生产 bridge、kernel、精度，也没有重新测出模型 TPS。
当前完整70层基准仍是约76 resident TPS。以下新增数据来自 module5 / PCIcd，
NUMA1 CPU与内存绑定的隔离最小实验；不能直接作为整模收益。
用户要求的本地留存继续执行，源码、失败、二进制、原始记录及分析全部留本地。

## 已找到的优先项：直接更新捕获图输入

源码链条确认了具体冗余：

1. serving runner 的 `copy_input_to_device` 调用 `async_h2d_copy`；未提供目标
   Tensor 时，每次 `empty_like(device='hpu')` 后 `copy_(non_blocking=True)`。
2. 当前 `serving/runner.py::_wrap_model_adapter` 明确设置
   `disable_tensor_cache=False`。不能只读 vendor 默认 True 而判断当前运行路径。
3. bridge `graphs.py::copy_to` / 缓存命中路径再将这些输入复制到固定 graph_inputs。
4. 因而通常经历“CPU数据→新HPU输入→捕获图固定输入”。不是同步 H2D，
   也不是权重读放大；浪费在动态小输入的分配、包装、暂存及二次复制。

本轮同一公开 `wrap_in_hpu_graph`、相同11个输入与整数加法、相同输出，比较：

| 输入方式 | 完成时间，两轮合格进程内正反配对 | 相对原方式 |
|---|---:|---:|
| 每步新建输入，再交缓存图 | 551.9–562.0µs | 对照 |
| 复用临时输入，再交缓存图 | 460.6–473.8µs | 少约84–94µs |
| 直接更新捕获时输入，再交同一缓存图 | 272.8–281.6µs | 少约275–284µs |

每输入宽度1/64/512个INT32，数值每步变化；两轮共3240次数值检查通过，进程
正常退出。计时含输入提交、graph replay及设备完成等待；输出正确性读取在计时外。
结果不是只缩短 enqueue。只有简单计算，没有HCCL、模型、并发图或用户别名。
首轮全局对象在解释器退出时遇到 bridge GC service 已销毁的异常，失败保留；
将探针 Tensor/graph 生命周期置于函数作用域、退出前销毁后，两轮正常退出。
这不证明 bridge 的一般退出问题已修复。

**实施位置**：复用现有 `NativeExecutionPlan` 输入绑定、现有 allocator 和
`device::copy_data_to_device(transfer_manifest)`；公开每次执行的输入更新能力，
让前端直接填充 bucket 的固定目标。固定输入缓冲由 graph/flight 拥有，而不是
在任意 `.to()` 下偷偷缓存返回 Tensor。并发执行、别名、原地修改和可变形状必须
保留独立语义，不能把这个孤立探针直接当可发布实现。

runner侧CPU元数据准备仍属于上层：当前真实模型 `_prepare_inputs` 约0.78–0.86ms，
其中约0.39–0.45ms是输入copy调用的合计（嵌套，不能相加）。探针说明这条路线
值得优先接入，但没有证明能从完整模型减去同样0.28ms，更不能把0.8ms全部划走。
只换 bridge 无法自动消除调用它之前的 Python 页表、列表和采样元数据构造。

## 已测的较小项：批量小DMA

复用同一 pinned源、目标地址、字节数和stream，只改提交组织：11次小copy及各自
完成记录，对比一次 `synMemCopyAsyncMultiple`、尾部完成记录。

每块4/64/512字节，两轮合格正反配对：完成时间30.5–30.9→23.4–23.5µs，
省约7.0–7.4µs；仅批量API、对照也不插逐copy事件时，省约4.4–5.6µs。
108次变输入/毒化目标验证通过，检查1188个范围。这证明微基准的真实收益，
但与上一项是同一输入链上的优化，不能重复记账。

bridge 已有批量 copy helper、地址租约和一次 producer 登记，不需新增DMA runtime。
批量描述符/固定staging的复用需要保留CPU源可修改、在途保活及错误处理语义。

## 反证：完成事件数量不是收益金额

相同输入、同一个已编译recipe、相同算术，改变每条/每8条/仅计时尾部的事件密度。
每次完整等待，32/144条recipe，每条1/8/32个TPC节点；无profiling、无SCAL interpose。

| 144条链，每条工作量 | 逐条事件→仅尾部：CPU提交 | 设备/完整完成结果 |
|---|---|---|
| 1个TPC节点 | 更快 | 两轮完成1208.9→911.6µs、1026.2→918.7µs；收益幅度波动明显 |
| 8个TPC节点 | 约1005–1009→878–884µs | 完成仍约2757µs，无收益 |
| 32个TPC节点 | 约1024–1027→894–899µs | 完成仍约9340µs；设备事件区间仍约9321µs |

两轮216次变输入检查、1,327,104个FP32值逐位通过。轻链会等CPU提交，减少事件
确实让它更早完成；重链提交成本已被计算掩盖，减少事件没有缩短关键路径。
探针没有模拟 bridge 的GC/allocator锁竞争、HCCL和早期Tensor可见性，因此不能
证明真实模型的区域资源优化无效；同样不能证明它值2ms。

已完成的70层合流实验140/141通信实际命中但TPS不涨，与这个反证一致。
**C/D仍是基础设施工作，但先证明真实模型哪一段被提交饿住，再给性能优先级。**
逐命令完成发布与资源保活也不能无条件删成一个尾事件。

## 另两条有价值、但尚未获得新增收益证据的路线

1. **正规扩大捕获范围到logits/采样的设备计算。** 旧约90TPS执行器捕获整个
   sample_tokens的SDK链，当前缓存图主要是forward。原始采样仍有Python元数据和
   mark_step边界；实测 `_run_sampling` 约0.53–0.59ms，其中准备约0.35–0.38ms，
   两者嵌套，而且可与前面的设备计算重叠。不能直接把0.55ms列为节省。
   bridge提供一般能力，vLLM选择捕获范围；不能向bridge加入token、KV页或greedy规则。
2. **消除真正的设备中间节点/物化，而非只改CPU循环。** 对已有硬件trace重新
   核对，仍执行 `pf_sum_bf16_bf16`、`pf_sum_f32_bf16`、`pf_combine_f32`、
   bitonic/router post、isfinite等节点。候选是归约与其消费者融合、路由链融合、
   同一图内消除可证明冗余的物化。需先证明具体生产者/消费者相邻与中间Tensor
   不逃逸，保留BF16中间舍入、全遮蔽页语义和跨卡依赖。不能仅按同名算子数推收益。

该trace来自上一轮较早二进制，且profiler把步延迟扰动到约22ms，只有结构诊断价值。
NIC执行事件缺失，不能称空白区为“所有引擎都空闲”。同名kernel的跨核心事件不能
相加成耗时；recipe会复用，唯一节点标签也不是执行次数。

## 优先级与下一道门

1. 优先补通用输入绑定/更新：取消临时HPU输入与固定图输入之间的多余一跳。
   在同模型、同捕获范围下只切换输入路径，测真正step完成；覆盖变内容、页边界、
   bucket切换、并发/在途生命周期。再验证batch和prefill，不先推广生产默认。
2. 将采样设备图接到同一执行核心，用同一输入/同一采样策略做范围对照。
   单独测输入改善、单独测捕获范围，不能一次改两者再归因。
3. 资源预编译/区域完成只针对证据指出的提交饥饿段推进；设备融合另按编译产物
   及消费者依赖验收。原算术不变的runtime实验与融合实验分别记账。

本轮确认了一个约0.28ms级的公开图输入优化、一个约7µs级的底层copy优化，
二者均为小图结果且不能相加。**尚未找到已经整模证明可回收的全部2–3ms**；
不承诺把这些项目相加就能从76走到90–100 TPS。
