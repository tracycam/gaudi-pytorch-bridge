本报告只核对已有代码、日志和运行状态，没有启动新的性能实验。

随后用户要求继续 bridge 内的优化分析，源码审计及方向另见
[通用优化方向](OPTIMIZATION-DIRECTIONS-20261004.zh-CN.md)。下文的暂停是本次

## 目标和当前结论

目标仍是把可复用的执行能力放进 Habana PyTorch bridge：普通应用继续使用
PyTorch/HPUGraph API，替换 bridge 安装即可受益，最终移除两个外置执行器。
这轮不改模型权重、精度或计算 kernel。性能是验证框架开销是否被消除的指标，
而不是再为一个模型另造执行路径。

已完成的关键部分是：bridge 能捕获并重放完整模型的计算/通信计划，不依赖外置
执行器。70 层 TP8 无 MTP 的同应用对照，B1 从约 49 提到约 75 TPS。
**90 TPS 尚未达到，两个外置执行器尚不能弃用。**

历史“60 → 90 TPS”不能直接替代本轮的实测对照。本轮先给 serving 建立明确的
`executor=pytorch` 普通路径，去掉外置 executor 及专用传输；之后 A/C 使用同一
冻结应用，只换 bridge。已证明这个应用的透明加速，还没有逐字复现任意历史
60 TPS 脚本，更没有证明任何 PyTorch 应用换 wheel 都能到 90 TPS。

## 整模型性能到底是什么

共同条件：MiMo-V2.6-Pro-RL、70 层、TP8、无 MTP、4K 上下文、128 输出 token、
B1/B2 各两轮。表中是模型驻留后的 decode；B2 是两请求聚合吞吐。

| 实验 | B1，两轮 TPS | B2，两轮聚合 tokens/s |
|---|---:|---:|
| 上游 `full-model-a3` | 49.05 / 48.62 | 92.49 / 97.63 |
| 核心候选 `full-model-c3`，413 | 75.04 / 75.42 | 118.69 / 118.76 |
| 413 追加诊断轮 `host-timing-70-c1` | 72.24 / 75.50 | 117.22 / 118.39 |
| prepared 候选 `prepared-model-70-c1`，503 | 74.57 / 76.26 | 116.61 / 118.52 |

第一对 B1 提高约 53–55%，B2 提高约 22–28%。每臂 6 条输出序列、768 token
完全一致，所有 8 rank 的两份图都命中新计划，无外置 executor 库加载。
每份图 284 条计划命令，其中 141 个 collective；这不是 284 个设备算子，
一条计算 recipe 内仍然可能有很多设备算子。

限制必须保留：

- 这是 fresh-process 对照，每臂两轮，不是同进程 ABBA。prepared 候选的细小变化
  没有足够证据超出跨运行波动，不能以最好一轮 76.26 宣称确定新增收益。
- 驻留 decode 从正常返回 token 的 step 中选择所有请求每步各出一个 token、
  已输出至少 16 个 token 的区间，保留每个原始 step，不按延迟筛选。
- 包含 prefill 的整个 generate wall 另有记录：首对 B1 约 18.9 → 21.9 tokens/s，
  B2 聚合约 22.4–22.8 → 23.8。不能把 75 当成含 prefill 的端到端吞吐。
- prompt 是重复的软件架构文本。输出相同证明执行等价，不构成独立语言质量验收。
- `full_model_qualified=true` 是完整层数、输出等价和执行覆盖通过；它不代表
  达到 90 TPS，也不代表完成模型质量或所有 graph 语义验收。

约 75 TPS 对应 13.33 ms/步，90 TPS 对应 11.11 ms/步，还需约 2.2 ms。
这个差值是待解决的目标差距，不是已找到、可以直接删除的开销。

## 现在这套代码实际怎么执行

1. 应用照常捕获 HPUGraph。编译层 `HabanaLaunchOpPT::ExportCapturedExecution`
   从 fresh/cache 接点导出 recipe、通信描述和抽象绑定。
2. `HPUGraph` 持有 bridge 内部 `NativeExecutionPlan`，保留 recipe、Tensor Storage、
   槽位与布局契约。值可以变化，分配/布局改变则不进入该快路径。
3. replay 先校验绑定。混合计划作为一个 job 交给已有 HCCL 工作队列；工作线程
   依次提交 compute/collective，调用方等待这一批 SDK 提交完成。
4. 每条计算命令仍调用 `RecipeLauncher::Launch`，处理地址锁、依赖事件、workspace、
   SDK launch 和异步资源回收。每条通信仍有自己的 SDK 提交。
5. 返回 Python 不等于设备完成。后续 logits、采样和读回结果沿普通框架继续执行。

已消除的是逐子图 Lazy cached-execute 路径，以及每个 collective 独立的
job/promise/future 周转。**一次 host 队列入队不等于一次硬件 launch。**
源码目前没有消除内部事件、把所有 recipe 合成一个，或让完整 token 自主在设备运行。

503 把 Tensor 引用列表、抽象依赖地址和通信描述准备移到 capture；仍每次重新锁定
物理地址，仍保留事件与完成回调。两 recipe 小图约省 0.5–0.7 µs，方向在机制上合理，
但不能把微基准的节省乘以命令数后当成模型收益。

架构已有收敛：本轮执行入口在 bridge，kernel 库只提供计算，serving 只负责模型与
调度。传统 bridge 路径仍作为兼容回退存在；外置两个执行器保留为历史对照资产。
“快路径和回退共存”不需要应用维护两套执行 API，但离移除外置工程仍有验收欠账。

## 真正未定案的问题：等待在哪里发生

现有诊断是 Python 函数的 host 墙钟时间，包含嵌套调用和可能的设备等待。
以 rank0 稳定 decode 区间的中位数为例，单位 ms：

| 函数边界 | 413 诊断 | 503 诊断 | 可以说明什么 |
|---|---:|---:|---|
| 输入准备 | 0.801 | 0.779 | 含输入拷贝及框架准备 |
| model.forward | 9.478 | 8.581 | 含 host 提交、队列和 SDK 调用；不等于设备计算 |
| compute_logits | 0.246 | 0.250 | host 函数历时 |
| 采样 | 0.559 | 0.539 | 含采样准备，不应再加其子调用 |
| 输出读回 | 2.045 | 2.304 | 可能主要在等先前设备工作，并非纯 DMA |
| 外层 sample_tokens | 13.500 | 12.839 | 包含上述多项，不能再相加，也不是主 TPS 计时 |

第一次诊断 rank7 的 forward 比 rank0 晚返回约 2.22 ms；它的读回仅 0.147 ms，
而其他 rank 多等约 2 ms。503 那一轮，晚返回变成 rank1（+1.88 ms）和 rank6
（+1.41 ms），rank7 仅 +0.28 ms。

这证明 host 返回/等待的位置会变，**不能证明固定某卡慢，也不能证明那 2 ms 全可省。**
仍需区分四种可能：CPU 实际执行与排队、线程被调度器停住、SDK 调用阻塞/反压、
必要的设备或跨 rank 依赖。现有数据不够对这四项分账。

NUMA 已有实证：运行期间 8 个 worker 及其线程均在本卡 PCI 所在 NUMA 节点 CPU
集合内。每节点 4 worker 共享一个 CPU 集合，尚未验证独占核心划分的收益；
允许内存节点为 0–1 不能证明所有页的实际归属。跨 socket 错绑不是已发现原因，
也不能因此宣称线程竞争或远端内存完全不存在。

仍逐命令执行的地址检查、锁、事件与回收，是源码可见的候选开销；当前没有证据
证明其中哪一项是剩余 2.2 ms 的主因。继续凭对象分配或事件数量猜热点，容易再做
一轮“微基准变快、整模型不动”。

## 恢复后按什么顺序做

| 顺序 | 工作 | 要回答的问题 / 完成条件 |
|---|---|---|
| 1 | 完成 CPU-only 诊断接线的最小构建与小图验证，继续 `-j 32` | 普通 CPU trace 不触发 HPU 初始化；能看到真实 C++ 提交线程跨度；启停和异常后恢复正确。失败就先修诊断，不加载 70 层 |
| 2 | 对冻结的同一候选采有界的 8 rank 提交时间线，性能测试仍关闭 profiler | 列出 binding preflight、入队/唤醒、RecipeLauncher、SDK/event 和最终等待；若 CPU trace 无法区分反压，补一段设备时间线。先解释等待转移，再选优化 |
| 3 | 只改占关键路径的已证实热点，走 bridge 通用接口 | 元数据热点才前移准备；队列/线程热点才试 NUMA 内核心划分；事件热点才考虑内部依赖合并。每项保持外部 stream 与生命周期语义，报告完整 step 的变化 |
| 4 | 对齐旧原生 90 TPS 与普通应用的剩余边界 | 分开对账 graph replay、输入 staging、采样、token 传输/RPC。若差距在 bridge 之外，要明确归属，不能把模型专用捷径偷偷塞回 bridge |
| 5 | 补兼容和生命周期验收，再删除外置执行器依赖 | 分布式在途 reset/销毁、communicator 生命周期、异常/回退一致性、动态输入/shape、B×T 与 prefill 等场景有明确结果；完整普通模型达到目标或明确报告未达原因 |

第 3 项不会先承诺省 2.2 ms。事件合并必须保留图外依赖、allocator 地址锁、
collective 顺序和资源有效期；不能通过删除正确性保障换取数字。
第 4 项尤其重要：旧原生执行器有特殊输入、采样和 RPC 路径，不能假设其全部优势
都来自 replay，也不能把“只换 bridge 90 TPS”写成已经得到的结论。

当前不应扩张到新 kernel、改精度、MTP 或再造一套 scheduler；先把已有框架路径
的剩余差距定位清楚。CPU profiler 是这一步的诊断工具，保持独立提交和最小范围，
不把它发展成另一个基础设施项目。
