# 通用框架：范围、边界与验收

2026-10-05。用户明确：目标是通用框架，而非一个模型的特例加速。
进一步明确：将优化抽象成通用能力，允许应用通过清晰接口使用，并能优雅迁移
到其他模型。应用零改动是兼容/收益归因的一种验收，不是禁止提供显式接入能力。
本文作为当前路线入口；旧实验文档保留历史事实，不代表通用能力已完成。

## 当前裁决

91.02 TPS 是修改后的 bridge **加 serving 适配**，在 MiMo 70 层、TP8、B1、
4K、greedy、无 MTP 下的驻留 decode 结果。它不是“原来约 60 TPS 的应用完全
不变，只换 wheel 达到 90”的证明。不得用该结果宣称其他模型已经获得收益。
当前有效 wheel 对应 bridge `47f28b972f9`，serving 为 `a450e13`。

交付目标是一份可安装的 bridge wheel、原有 PyTorch/HPU Graph API、一套
框架资源与提交实现。已有应用无需导入外置 executor。新模型使用已支持的
算子和图契约时，不应修改执行核心。通用不等于所有输入都走同一快路径：
尚未支持的行为应保持原语义并明确回退，不能以静默降级掩盖支持缺口。

## 责任边界

| 层 | 应当负责 | 禁止承接的职责 |
|---|---|---|
| PyTorch bridge | 捕获、缓存、绑定、Tensor/地址生命周期、依赖、计算/通信/拷贝提交 | 模型名、层数、专家路由、KV 页表算法、token 更新、接受拒绝规则 |
| vLLM 集成 | 声明可捕获计算范围、把 scheduler 结果写成输入、采样/KV 状态语义 | 自建 SDK 提交循环、独立 stream/allocator 或第二套图执行器 |
| 模型与算子 | forward、权重格式和计算算法 | 为更换 bridge 重写模型，按具体模型选择执行引擎 |

已有 `HPUGraph` / `wrap_in_hpu_graph[_func]` 是产品入口；
`NativeExecutionPlan` 是 bridge 的内部实现，不是另一个让用户选择的产品。
不增加 GraphManager、执行器包装包或部署时源码补丁层。

桥内能通用消除的开销应自动消除；不能从 framework 推断应用语义时，使用
清晰的上层契约，而不是猜测 KV 是否不变或哪些输入可以不更新。
Python scheduler 没有提交给 bridge 的工作不能凭空被图优化掉；扩展捕获范围
必须记作集成层改动，不能算作“只换 wheel”。

## 应用可使用的能力，而不是模型专线

| 能力 | 应用提供什么 | 框架负责什么 | 目前状态 |
|---|---|---|---|
| 可重放的计算范围 | 一个符合捕获契约的函数/Module | 捕获、编译缓存、执行计划、依赖与生命周期 | 原有 wrap/HPUGraph 入口已接新实现；支持范围仍有限 |
| 稳定输入绑定 | 固定布局的 Tensor；每步的新内容 | 保留绑定、校验有效性和失效处理 | 静态路径已验证，新分配重绑不能笼统宣称命中快路径 |
| 批量输入上传 | 源/目标 Tensor 列表及 non_blocking 语义 | 类型表示、合法批处理、完成依赖和回退 | 标准 `_foreach_copy_` 后端已有实现 |
| 输入结构处理 | 普通容器/dataclass，而非模型名 | key/拷贝遍历与语义保持 | 已实现；不是任意 Python 对象图编译器 |
| 形状/模式切换 | 实际形状与需专门化的控制参数 | 沿用图缓存与明确回退 | 原有缓存存在；跨模型/动态调度覆盖待补 |
| 覆盖及回退诊断 | 无模型内部字段 | 提供计划覆盖、失败与回退原因 | 目前仍为私有诊断，公共稳定接口待收敛 |

应用接入原则：首先复用上述已有入口。新增公开接口必须弥补明确缺口，不能
只包装已有函数。通用 vLLM 适配由一个地方实现；模型只表达 forward、输入和
状态生命周期。不能要求新模型复制 `PreparedDecodeInputs`、读取另一个模型
的私有 runner 字段，或注册专用 SDK 提交器。

迁移步骤与接口示例见 [APPLICATION-INTEGRATION.zh-CN.md](APPLICATION-INTEGRATION.zh-CN.md)。

## 已有能力和缺口

- bridge 已有通用的 prepared region、绑定去重、地址世代检查、GIL/锁修复、
  容器遍历和小输入 foreach H2D。它们的准入条件与模型名字无关。
- foreach H2D 只优化已有 `_foreach_copy_` 调用。现阶段不会自动把任意分散
  `copy_` 合并；未来若扩展，必须证明中间读写、别名和跨流依赖允许合并。
- serving 的输入缓存按请求、页表、布局校验，但当前只接纳同步 unit-query
  decode；step graph 主要接纳无惩罚、无 logprobs 的 greedy。prefill、MTP、
  异步调度、LoRA、PP/DP 等未纳入这次快路径验收。
- 去掉 KV 参数树依赖当前 HpuModelAdapter/模块绑定契约，不能直接推广为
  “所有模型的 KV 参数都可以删除”。
- 独立 Torch 功能探针已存在；第二个真实模型的整模型收益仍待测。
- 旧执行器未在 91 TPS 进程中加载，但仓库退役工作未全部完成。

## 实施顺序

### 1. 恢复框架独立验收

沿用现有验证工具、隔离 venv、源码归档和 SHA，不新建压测框架。

| 应用源码和配置 | 上游 bridge | fork bridge | 证明什么 |
|---|---|---|---|
| 冻结的原应用 | A | B | B/A 才是原应用只换 bridge 的收益 |
| 同一份整理后的通用 vLLM 集成 | C | D | D/C 是集成后 bridge 收益；C/A、D/B 是集成贡献 |

每一行的模型、内核、权重、精度、请求、采样、捕获范围和输入准备必须相同。
不同 wheel 使用独立进程、交错重复；不能把同进程开关对照说成换 wheel。
如果某组合因 API 不兼容无法运行，应记为阻塞，不得偷偷替换应用。

首个修正：`benchmark_native_graph_submission.py` 的 fork 私有统计接口改为
可选，仅 `--require-native` 明确要求它；记录基准脚本 SHA。无该接口的上游
也运行同一计算、正确性检查及计时循环。该修改不改变生产执行路径。

验收：保存两边应用/配置/内核哈希、wheel 身份、真实路径覆盖、输出及完整
墙钟；主机 enqueue 单列，不能冒充设备完成或端到端收益。

### 2. 收敛输入和捕获契约

先复用现有 graph 缓存、Tensor 绑定和 copy 接口，不立即引入新 public API。
将稳定结构与每次变化的内容分开；定义形状、alias、对象替换、地址搬移、
CPU 源异步读写和缓存失效规则。通用机制进入 bridge，token/KV 状态更新留在
vLLM。集成应形成该 runner 的公共能力，不需要每个模型抄一套适配器。

验收：独立于 vLLM 的 Torch 程序覆盖嵌套输入、同对象内容变化、新分配、
形状桶切换、view/alias、原地更新、图外消费者和跨流访问；不靠 MiMo 私有对象。
支持和回退都过正确性门，失败后的部分提交不得重试整个图。

### 3. 扩展真实负载覆盖

先选择至少一个不同结构的真实模型，使用相同 vLLM 集成且不修改 bridge 核心。
再扩展 decode batch、prefill chunk、采样及 speculative 的状态契约。它们
共用图执行基础设施，上层数据布局和调度语义不必相同。

验收分开记录：功能正确、快路径覆盖、相对上游的整模型收益。第二个模型
尚未跑前不得承诺收益；prefill 记录 TTFT/tokens/s/显存，decode 记录每流和
聚合吞吐、步延迟及尾部。计算受限场景不要求虚构加速，但需检查性能回退。

### 4. 删除重复实现

已证明替代的功能才退出生产依赖。统一 ordinary/prepared 命令的资源管理
与底层提交，保留必要的能力回退，删除历史选择标签和模型专用执行捷径。
旧执行器仅留历史资产，不成为长驻的产品选项。

验收：干净环境只安装 bridge、算子和正常 serving 集成；无旧执行库/preload，
新增模型不改运行时核心。保留 91 TPS 组合基准防止整理回退，但不把它用作
第一阶段“只换 bridge”的替代证明。
