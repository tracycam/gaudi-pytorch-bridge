# 同一模型命令链的提前提交实验

目标仍是 PyTorch bridge 上 70 层、TP8、B1、无 MTP 的真实推理 ≥90 TPS。
这里记录诊断证据，不把设备区间的倒数当成模型 TPS。

## 问题与方法

完整 step 捕获只有约 78 TPS。为区分提交晚到与设备执行成本，复用已有的
TPC delay kernel，在完整 step 前放置有界门控。门控后经过一次跨 rank
设备对齐，再记录 compute stream 的开始事件、执行原来的完整 step、记录
结束事件。所有模型命令仍由同一个 bridge 提交，没有录制器代为重放。
正常组没有门控；两组都先 drain 输入并经过 CPU barrier。

门控组必须在所有模型调用返回后，仍能查询到结束事件未完成；这证明 host
确实有机会提前提交。门控时长、输入准备、CPU 输出处理不计入设备区间。
门控改变了启动对齐和缓存状态，因此结果是可行空间的诊断，不足以单独把
全部差值定性成 CPU 指令开销，更不是可以用于生产的延时技巧。

## 结果

`bridge-prequeue-20261005/results/model70-d`，同一驻留模型内 normal/gated/
gated/normal 重复两轮，每个 rank 各四个样本：

| rank | 正常设备区间 ms | 提前提交设备区间 ms |
|---:|---:|---:|
| 0 | 11.812 | 9.616 |
| 1 | 11.869 | 9.711 |
| 2 | 11.890 | 9.656 |
| 3 | 11.871 | 9.694 |
| 4 | 11.805 | 9.690 |
| 5 | 11.868 | 9.611 |
| 6 | 11.884 | 9.675 |
| 7 | 11.868 | 9.702 |

全部门控样本通过 prequeued 和 complete_step 检查。CPU 提交仍约 7.8–8.5ms。
实验后查询的 8 卡 SOC 时钟均为 current=max=1650MHz；没有逐步时钟采样。
普通未门控推理仍约 78–79 TPS，不能据此宣布达到 90。

## 测量纠错

早期 source-c 用 `torch.hpu.Event.elapsed_time`。bridge 的该接口汇总多个
子流取最大值，空闲 DMA 子流的时间会把 CPU 提交纳入结果，不适合本实验。
source-d 改为只在实际 compute stream 上记录原生计时事件。观察库只转发
原 SDK launch 一次、识别 stream，不保存或重放命令。早期结果全部保留，
不用于上表。不能把两个版本的数据混在一起。

## 对应实现

bridge `0ea00c3cdc` 在已有 `NativeExecutionPlan` 的已证明同流区段中，合并
依赖检查与 producer 完成事件，保留每个原有 Tensor、地址锁、recipe、
communicator 和清理回调。入口处理外部依赖，出口发布读写完成；遇未知操作
先发布已提交前缀，再恢复普通处理。默认关闭，通过图对象接口选择。

32 线程构建通过。TP2 FP32/BF16 通信链、跨流消费者/写入者、混合 peer 回退、
peer 尚未提交时销毁图的资源保留检查通过。两层模型 B1/B2 的首步及 KV 页边界
完整 logits 逐位一致，短链性能没有明确收益。

## 整模型反证：只合并事件没有收益

`bridge-event-batch-20261005/results/model70-a`：同一驻留模型 event off/on/on/off，
70 层、TP8、4K、160 个输出 token，连续 coordinator wall：

| batch | 原完整 step ms | 合并事件 ms | 吞吐 |
|---:|---:|---:|---:|
| 1 | 12.922 | 13.159 | 77.39 → 75.99 TPS |
| 2 | 16.526 | 16.707 | 121.02 → 119.71 聚合 tokens/s |

两种 batch 的全部输出一致。首个 decode、KV 页边界前后，完整 logits、
输入 token、位置均逐位一致。8 rank 均实际走候选计划，没有外部执行器。
事件合并未被中断。**正确性通过，性能失败；保留默认关闭。**

独立轻量 host 观察（嵌套时间不可求和），rank0：CPU 执行调用
7.842→7.090ms，输出 CPU 返回等待 3.878→4.897ms，sample_tokens 总范围
12.545→12.799ms。它确实减少了 CPU 提交工作，但未转化为设备关键路径收益。
不能继续沿“事件数减少，所以设备必然更快”推导；也不能把约 1ms 的输出
等待增长误称为四字节拷贝本身变慢。

下一步用不启用设备 profiler 的公共 API 计时，区分 SDK launch、HCCL、
事件提交和 bridge 其余工作。GC 线程的 event synchronize 与提交重叠，
必须单列，不能将多个线程 inclusive 时间直接相加成一步延迟。
